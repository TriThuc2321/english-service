Auth flow

How authentication works between english-service (BE), english-backoffice (BO, React SPA) and english-student (Next.js, whose server acts as a BFF).

BE english-service BO client = bo Student client = web

At a glance

Backoffice bo Student web
Access token Held in the SPA's memory, sent as Authorization: Bearer httpOnly cookie st_access_token on the student domain. The BFF attaches the Bearer header
Refresh token httpOnly cookie refresh_token_bo set by the BE (path /api/auth, SameSite=Lax, Secure) httpOnly cookie st_refresh_token on the student domain. The BFF sends it in the body
Google login result BE sets the refresh cookie and redirects to /login BE redirects with ?code= (a single-use refresh token valid for 60s) and state=clientNonce
Login CSRF defence oauth_state cookie on the API domain oauth_state (API) + oauth_nonce (student domain)
CMS endpoints Allowed (@Clients(AuthClient.BO)) 403

4.Refresh token rotation (POST /auth/refresh)

Each login session is one auth_sessions row; a refresh updates that row in place (new jti) instead of adding rows, so the table only grows with the number of sessions. Reusing an old token of a session outside the 30s window is treated as theft, and all of the user's sessions are revoked.

5.Email and password accounts

Codes live in email_codes: one row per (user, purpose), stored as a sha256 hash, valid for 10 minutes and 5 attempts, and a new code replaces the previous one. A code is sent at most once per 60s. Mails go through MailService (Resend) without being awaited, and every response is identical whether or not the email exists.
